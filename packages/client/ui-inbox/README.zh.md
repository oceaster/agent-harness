# @deepseek-ai/dsh-client-ui-inbox

[English](README.md) | 中文

这个家庭部署插件为登录用户可使用的每个助手提供一个固定的侧栏收件箱行。通过身份验证的 e-server API 提供名单、名称、会话标识和频道列表；浏览器不内置家庭助手名单。

## 导航与频道

助手行通过 `/v1/browser/inbox/open` 解析其固定会话。控制器先刷新运行时会话列表，再选择返回的标识，以便输入区绑定已存在的会话。打开行不会任意创建客户端会话。工作目录由 e-server 按助手配置。

助手频道通过布局的 `conversation.page` 插槽占据中央聊天区。频道行与收件箱行具有相同的完整宽度和选中反馈。两种行都通过下拉菜单和确认框提供清空操作。频道页面只显示记录和刷新按钮，没有输入、编辑控件或模型生命周期。没有消息的频道显示未选中欢迎页所用的家庭标记，而不是一句提示文字；正在读取或读取失败的频道仍显示自己的加载或错误提示行，不会显示该标记。选择助手行会恢复其会话，不会中断正在进行的工作。

后端按登录用户隔离频道记录、可用组合和清空操作。清空频道会删除共享记录和未发送的通知；已接收的消息仍保留在接收助手的会话中。

## 一个外壳中的两个界面：子代理侧栏

Owen，2026-10-23：「2 separate interfaces BUT SAME SAME, DIFFERENT, BUT SAME」。本包只填充一个侧栏区域，填充哪种正文取决于本次页面加载属于哪个界面：Delta 入口（没有 URL 片段）得到 `InboxPanel`——助手行与助手频道——Epsilon 入口（`#epsilons`）得到 `EpsilonPanel`，即 Delta 的子代理列表。`surface.ts` 掌管这个判断，只在启动时读一次 `location.hash`；`sidebar.workspaces` 是单槽位，因此不属于本次页面加载的那个界面根本不会被挂载，其标记在 DOM 中是不存在，而不是被隐藏。切换界面就是一次页面加载，这也正是两个入口各自都是可分享链接的原因。包裹本应用的 e-server 页面把同一个片段附加到 iframe 的 `src` 上，因此 `EPSILONS_FRAGMENT` 是两端共用的那一个词。

**子代理不在收件箱侧栏里。** 正在阅读收件箱或同伴频道的人只会看到自己的助手和频道，其他什么都没有；Epsilon 界面的树里根本没有助手行或频道区域。

**名单属于 Delta，而不属于当前面板。** Epsilon 侧栏列出登录用户 DELTA 会话的直接子会话——`/v1/browser/inbox` 为该用户解析出的目录，通过 `sessions.refreshSubagents(parentSessionId)` 刷新——因此任何工人打开之前列表就已经存在，打开一个工人也不会把它清空。改为读取当前打开会话的目录，正是让列表只在工人已经显示在屏幕上时才出现的原因，那不是 Delta 子代理的列表。

每个工人行与助手行使用同一个行组件和同一套样式——头像、状态点、名称、一行状态——第二行是 harness 记录的持久创建标签（即交给工人的任务）。工人在自己那一行只用长格式命名一次（`Epsilon 3`），短格式（`E3`）是头像字母，行内不会重复打印名称。harness 枚举到但无法识别的子会话会显示为损坏行且没有启动控件，因为 harness 给出的原因就是事实，本面板无法修复。这里没有行菜单：无法从此处清空工人。

打开工人时，会把该行携带的确切地址（父会话、子会话、模式）交给 `sessions.openSubagent`；不请求任何东西，也不创建任何东西。随后对话列用 harness 自己的组件渲染该工人——`ConversationRoot`、`ChatView`、`AssistantMarkdown`、`MessageItem`。本包不绘制任何对话记录、气泡或消息行：这里没有第二份聊天表面可以漂移，工人的会话也不会显示父子层级面包屑（会话头部不渲染任何内容）。

只读是 fork 的规则，不是本面板的规则，而且本部署的规则比「换一个只读输入区」更强：`ConversationRoot` 只在 `readOnly` 为假时才绘制输入位，而 `readOnly` 等于 `child || childSummary`，因此子代理会话（无论按地址打开还是按列表打开）在树中根本没有输入位——一次性工人和可继续工人都是如此。任何 CSS 都无法造成这一点，这里也没有尝试。（`SubagentReadOnlyComposer` 仍是为「保留输入位」的部署准备的组合位；在本 fork 中，`!readOnly` 判断先一步解决了它。）

行跟随 harness 的选择，因此在 Epsilon 界面中打开的工人就是当前行；工人打开时没有任何助手行声称它是当前行，正如没有助手行会声称拥有不属于它的会话。

## 在线状态与未读轮次

名单包含已禁用的助手；其行显示离线和已禁用，不能启动会话。绿色代表在线，红色代表离线，白色圆点加旋转圆环代表正在工作（启用减少动态效果时显示静态开口圆环），蓝色代表有未读的已完成回复，琥珀色代表终止轮次的致命错误。频道只有在双方都可用时显示绿点。模型重试和可恢复的工具错误不会产生琥珀色状态。

助手自己的轮次正在运行，或其下任意深度的会话仍在运行时，该行显示正在工作，并使用该助手自己的动词：Delta 和 Darwin 显示 `正在工作...`，Diana 显示 `聊天中...`，Dexter 显示 `思考中...`，当前版本不认识的助手显示 `正在工作...`。当行数据报告有等待工作名额的委派（`queuedWorkers`，属于服务器知识，浏览器无法推导；没有该字段即视为没有排队）时，该行同样显示正在工作，因为尚未完成的工作不算空闲，即使此刻还没有任何东西在运行。该行只显示一个数字，而且始终只有一个：全部在办工作的总数。`正在工作... (4)` 表示三个正在运行的子助手加上一个仍在排队的委派，圆点的无障碍标签和标题使用同一个字符串；在这个外观中子助手不可见，因此父行是显示它们工作的位置。这里没有“正在工作/总数”的一对数字——所有者认为 `Working... (3/4)` 是坏的——没有任何在办工作时保留纯动词 `正在工作...`，因此永远不会出现 `(0)`。正在运行的部分跟随客户端会话存储，子助手开始或结束会在一帧内更新该行，无需刷新收件箱；排队部分跟随行数据，排队的委派离开队列会在该行本来就会执行的下一次常规收件箱读取时体现，因此可能有一个刷新周期的滞后。

完成轮次与致命错误标记来自可信主机事件，按用户与助手的固定会话持久保存。当相应会话被选中、可见且空闲时，浏览器只确认它实际显示的完成序号。即使确认操作与后续完成事件竞争，新的回复仍保持未读。阅读频道或子助手不会将父助手收件箱标为已读。

竖屏只改变形状，不改变内容。浏览区域从侧边栏外壳收到 `portrait`：此时轨道只画头像——每个助手行一个字形、每个频道行一个字形，各自保留本行的可访问名称（`打开与 X 的对话`，或频道自己的名称）以及 `aria-current` 选中状态；点击字体会在当前视图打开该对话，而不是把收件箱铺到聊天上。每次选中（助手行、轨道字形、频道行）都会先调用 `collapseOnSelection`，因此选中的对话一次点击就恢复整屏；该回调只在竖屏生效，列已收起时为空操作，所以手动展开绝不会被渲染撤销。状态文案（`正在工作... (4)` 等）、时间戳、分区标题、菜单、刷新控件和设置标签在轨道模式下根本不渲染，而不只是隐藏。

## 扩展点

插件占据 `sidebar.workspaces`，并注册 `agent-channel` 中央页面。插槽注入发布控制器快照和回调；组件只渲染这些属性。这个部署不组合会话列表、工作目录浏览器和新建会话插件。

## Model Experience

无；收件箱导航和频道渲染不注册模型上下文，助手通知的投递由 e-server 主机插件负责。

#### KV Cache effect

无；这个浏览器插件既不组装提供商请求，也不写入会话事件。

## Known Limitations and Deferred Work

- 浏览器同源位置必须提供家庭 e-server 收件箱和频道 API。
- 频道选择是临时状态，重新加载会重置选择；后端保留记录。
- 频道记录显示最近 200 条消息，并在选中时刷新。
